# Geometry and witness contract

This is a proposed mathematical/data interface, not an implemented library or audited proof. Its formulas can drive exploratory geometry; their relationship to set-based packing should later be proved in Lean.

## Coordinates

Use a container $[0,L]\times[0,L]$, mathematical $y$ increasing upward, and unit small-square side. Square $i$ has center $p_i=(x_i,y_i)$ and counterclockwise angle $\theta_i$ in radians. Set

$$
u_i=(\cos\theta_i,\sin\theta_i),\quad
v_i=(-\sin\theta_i,\cos\theta_i).
$$

Its vertices are $p_i\pm u_i/2\pm v_i/2$. A renderer may flip $y$ with a camera transform. An importer must convert screen coordinates explicitly.

A square's orientation is periodic modulo $\pi/2$, so $[0,\pi/2)$ is a valid per-square canonical range. Restricting **each** square to $[0,\pi/4]$ would discard configurations: reflecting one square independently is not a symmetry of an arbitrary packing. Whole-container reflection is a valid symmetry of the whole configuration.

## Containment

The axis-aligned half extent in either coordinate is

$$
h_i=\frac{|\cos\theta_i|+|\sin\theta_i|}{2}.
$$

Containment is equivalent to all four margins being nonnegative:

$$
x_i-h_i,\quad L-x_i-h_i,\quad y_i-h_i,\quad L-y_i-h_i.
$$

Checking centers alone is insufficient for rotated squares.

## Pair separation

For a unit direction $a$, the projected half extent is

$$
r_i(a)=\tfrac12\bigl(|a\cdot u_i|+|a\cdot v_i|\bigr).
$$

For a pair define

$$
g_{ij}(a)=|a\cdot(p_j-p_i)|-r_i(a)-r_j(a).
$$

The separating-axis criterion for squares gives

$$
\operatorname{interiorDisjoint}(i,j)
\iff
\max_{a\in\{u_i,v_i,u_j,v_j\}}g_{ij}(a)\geq0.
$$

Equality permits contact. The four axes are sufficient because they are the edge-normal directions of the two squares. Establishing this equivalence is an explicit formalization milestone, not an assertion that mathlib already exposes the desired lemma.

For floating-point preview, use a named $\varepsilon>0$: margin below $-\varepsilon$ is a detected violation; values within $\pm\varepsilon$ are near contact/uncertain; larger margins indicate numerical clearance. A tolerance-based pass is **approximate**, not rigorous feasibility. Report the minimum wall margin and the minimum over pairwise maximum separation margins. For $n=1$, report pair margin as absent rather than inventing a value. Pair checks cost $O(n^2)$ initially.

## Exact and interval representations

Store submitted decimal values as strings so their original digits survive. A finite decimal can denote an exact rational value for a coordinate; a decimal angle still needs rigorous trigonometric evaluation to certify its square.

For exact orientation data, use $(c,s)$ with the proved constraint $c^2+s^2=1$, and set $u=(c,s)$, $v=(-s,c)$. Rational orientations can be generated by

$$
c=\frac{1-t^2}{1+t^2},\qquad s=\frac{2t}{1+t^2}
$$

for rational $t$. This yields exact unit squares. It is a subset of all real orientations, so rational-orientation search alone is not exhaustive. The five-square $\pi/4$ construction naturally uses algebraic coordinates instead.

A rigorous interval checker must use outward rounding and return `inconclusive` when it cannot decide a sign. Exact contacts frequently require symbolic arithmetic or a certificate tailored to a chosen separation axis. More digits alone do not establish a rigorous enclosure. Rationalizing a placement changes it: recheck every wall and pair afterward. Slightly enlarging the container may help repair a candidate, but does not automatically remove all square-square overlaps.

## Proposed interchange version 1

Keep the original imported artifact alongside its normalized form. Minimal example, deliberately labeled as a candidate:

```json
{
  "schema_version": 1,
  "id": "manual-n001-0001",
  "problem": "congruent-unit-squares-in-square",
  "n": 1,
  "container_side": "1",
  "coordinates": {"origin": "bottom-left", "y_axis": "up"},
  "orientation_encoding": "radians-decimal",
  "squares": [
    {"id": "q000", "x": "0.5", "y": "0.5", "theta": "0"}
  ],
  "provenance": {"method": "manual", "parent_id": null, "source": null},
  "evidence": {"status": "candidate", "reports": []}
}
```

Validation requirements: supported version and conventions; positive finite $L$; positive integer $n$; exactly $n$ poses; unique IDs; finite decimal strings; consistent orientation encoding. Never silently drop an unparseable pose. Future exact encodings should have explicit rational/algebraic schemas, including an isolating interval for polynomial-root expressions.

Store verification in an immutable report tied to the witness's byte hash: checker commit, method, arithmetic model, precision/tolerance, command, result, margins, timestamp, and any certificate hash. Changing one pose invalidates its old report. A displayed status must be derived from the report, not trusted from imported JSON.

Record search settings separately: PRNG algorithm and seed, solver/configuration hash, platform, evaluation or step budget, wall time, starting witness, and output hashes. Use an adapter for each upstream format; do not assume another project's witness or snapshot schema matches this proposal.

## Geometry checks to implement with the code

Use edge contact, corner contact, tiny gaps/overlaps, coincident squares, rotated wall contact, invalid inputs, and the five-square construction. Include rotated pairs whose axis-aligned bounding boxes overlap while the squares do not. For exploratory numerics, compare separating-axis results against an independently implemented polygon-intersection diagnostic away from contact. Such checks catch implementation errors; they do not replace the formal equivalence proof.
